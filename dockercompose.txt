Docker init
-----------

`docker init` is a Docker CLI command that helps prepare an application
project for Docker. It interactively examines the project and can generate
starter Docker files, such as a `Dockerfile`, `.dockerignore`, and a Compose
file. The files it generates depend on the project and the prompts you select.

Run it from the application project directory:

```text
docker init
```

Review and adjust the generated files for your app before using them. For
example, check the build steps, ports, environment variables, and any
credentials. `docker init` scaffolds configuration; it does not build the
image or start the containers.

docker init is designed to initialize Docker configuration for an application in the current directory. It does not automatically containerize all 12 microservices or generate a complete production-ready Compose file for your entire architecture.

After reviewing the files, build and start the Compose services with:

```text
docker compose up --build
```

Sample Docker Compose file
--------------------------

The following example runs a web container and a PostgreSQL database. The web
service is built from a Dockerfile in the current directory. Both services
join the same network, so the web application can reach the database using
the hostname `db`. Each container also has a fixed IP address on a custom
subnet, and both services use a restart policy.

Create a file named `compose.yaml`:

```yaml
services:
  web:
    build: .
    restart: unless-stopped
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    ports:
      - "8080:3000"
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: appdb
      DB_USER: appuser
      DB_PASSWORD: change-me
    depends_on:
      db:
        condition: service_healthy
    networks:
      app-network:
        ipv4_address: 172.28.0.10

  db:
    image: postgres:16
    restart: unless-stopped
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      app-network:
        ipv4_address: 172.28.0.20

volumes:
  postgres-data:

networks:
  app-network:
    driver: bridge
    ipam:
      config:
        - subnet: 172.28.0.0/16
          gateway: 172.28.0.1
```

The current directory must contain the web application's `Dockerfile`. The
application should listen on port 3000 and use the `DB_HOST`, `DB_PORT`,
`DB_NAME`, `DB_USER`, and `DB_PASSWORD` environment variables to connect to
PostgreSQL. Replace the sample password with a suitable secret for your
environment; do not use a sample password in production.

Restart policies control whether Docker automatically starts a container
again after it exits:

- `no` (default): Do not automatically restart the container.
- `always`: Restart it whenever it exits, regardless of the exit status. If
  you manually stop it, Docker does not restart it immediately, but it can
  start again when the Docker daemon restarts.
- `unless-stopped`: Like `always`, but a container you manually stopped stays
  stopped after the Docker daemon restarts. This is the policy used in the
  sample.
- `on-failure`: Restart only when the container exits with a non-zero status.
  It does not restart the container just because the Docker daemon restarted.

For example, limit retries after a failure to five attempts:

```yaml
restart: "on-failure:5"
```

Choose a policy that fits the service. `always` or `unless-stopped` is common
for long-running services, while `on-failure` is useful when only failed
exits should trigger retries. Restart policies do not replace application
health checks or fix an application that repeatedly crashes.

Logging configuration
---------------------

The `logging` section selects how Docker collects and stores a container's
stdout and stderr output. In this example, the `json-file` driver stores the
logs as files on the Docker host. The options limit each log file to 10 MB and
keep up to three files per container, rotating older logs to help prevent
unbounded log growth.

View a service's logs with:

```text
docker compose logs -f web
docker compose logs -f db
```

Applications should write their logs to stdout or stderr so Docker can collect
them. Logging-driver support and options can vary by Docker environment.

Health checks
-------------

A health check periodically runs a command inside a container to determine
whether its application is ready and functioning. The database example uses:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
  interval: 5s
  timeout: 5s
  retries: 5
```

- `test`: Command Docker runs; `pg_isready` checks whether PostgreSQL accepts
  connections.
- `interval`: Wait five seconds between checks.
- `timeout`: Allow each check up to five seconds to finish.
- `retries`: Mark the container unhealthy after five consecutive failures.

Docker reports health as `starting`, `healthy`, or `unhealthy`. In this Compose
file, `depends_on` with `condition: service_healthy` makes Compose wait for
the database health check to pass before starting the web service. A health
check does not itself restart an unhealthy container; restart policies react
to container exits, not just an unhealthy status.

The network's subnet is `172.28.0.0/16`, with gateway `172.28.0.1`. The web
and database containers are assigned `172.28.0.10` and `172.28.0.20`. Ensure
this subnet does not overlap with networks already used by your host, VPN, or
other Docker networks. Static container IPs are usually unnecessary; Compose
service names such as `db` are more portable and are preferred for service
discovery.

Volumes do not have IP addresses or subnets. The `postgres-data` volume is
storage mounted into the database container; networking settings belong to
the containers and their Docker network.

Start the services:

```text
docker compose up -d --build
```

See service status and logs:

```text
docker compose ps
docker compose logs -f
```

Stop and remove the containers and network:

```text
docker compose down
```

The named `postgres-data` volume is retained when you run `docker compose
down`, so database data persists. To also remove the volume and its data, run
`docker compose down --volumes`.


Command	Stops containers	Removes containers	Removes images
docker compose stop	Yes	No	No
docker compose down	Yes	Yes	No
docker compose down --rmi all	Yes	Yes	Ye


Start those same containers again:
docker compose start
