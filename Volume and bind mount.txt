Volume:

Will mount a logical seperated volume created in HOST itself to a container.

Volumes are persistent data stores for containers, created and managed by Docker. You can create a volume explicitly using the docker volume create command, or Docker can create a volume during container or service creation.

When you create a volume, it's stored within a directory on the Docker host. When you mount the volume into a container, this directory is what's mounted into the container. This is similar to the way that bind mounts work, except that volumes are managed by Docker and are isolated from the core functionality of the host machine.


Volumes are the preferred mechanism for persisting data generated by and used by Docker containers. While bind mounts are dependent on the directory structure and OS of the host machine, volumes are completely managed by Docker. Volumes are a good choice for the following use cases:

Volumes are easier to back up or migrate than bind mounts.
You can manage volumes using Docker CLI commands or the Docker API.
Volumes work on both Linux and Windows containers.
Volumes can be more safely shared among multiple containers.
New volumes can have their content pre-populated by a container or build.
When your application requires high-performance I/O.

Volumes use rprivate (recursive private) bind propagation, and bind propagation isn't configurable for volumes.

What if you use a different container path?
You can use /backup instead of /data:
docker run -dit --name app4 \
  --mount source=shared-data,target=/backup \
  ubuntu:latest bash


Then access the same file using:
docker exec app4 cat /backup/message.txt


It works because the volume is the same; only its mount path inside the container has changed.

Use docker volume prune to remove the datas in the volumen and rm the volume.

Case 1: Mount a non-empty volume
Suppose your Docker volume already contains a file:

shared-data volume:
message.txt
Hello from the volume


Your container image already has a file at /data/message.txt:
/data/message.txt
Hello from the image


Now mount the volume:
docker run -it --name app1 \
  --mount source=shared-data,target=/data \
  ubuntu:latest bash


Inside the container, run:
cat /data/message.txt


Output:
Hello from the volume


Why? The volume is mounted over /data, so the pre-existing file from the image is obscured. It isn't deleted; it's just hidden while the mount is active.
Before mounting
Container image

/data/message.txt

Hello from the image

Volume

message.txt

Hello from the volume



After mounting at /data
Visible file: Hello from the volume

The image's file is obscured, not overwritten.


Case 2: Mount an empty volume
This case is different. Suppose the image already contains:
/data/
└── message.txt
    Hello from the image


You create an empty volume:
docker volume create empty-data


Then mount it:
docker run -it --name app2 \
  --mount source=empty-data,target=/data \
  ubuntu:latest bash


By default, Docker copies the existing contents of /data into the empty volume.

So when you run:
cat /data/message.txt


You get:
Hello from the image


The file has been copied into the volume, and the container sees it through the mount.

Why is this useful? For example, an image may include default configuration files or website content that you want to initialize into a new volume.
Case 3: Prevent Docker from copying the existing files
You can disable this automatic copy with volume-nocopy.
docker volume create empty-data2

docker run -it --name app3 \
  --mount type=volume,source=empty-data2,target=/data,volume-nocopy \
  ubuntu:latest bash


Now, if the image had files in /data, they won't be copied into empty-data2. The mounted directory will appear empty unless you create files there yourself.
Try this practical experiment
This makes the behavior especially clear because we create a custom image with a file already inside /data.

1. Create a Dockerfile
FROM ubuntu:latest
RUN mkdir -p /data && echo "File from image" > /data/message.txt

Build the image:
docker build -t volume-demo .


2. Run without a volume

Output:
File from image


3. Run with an empty volume
docker volume create demo-data

docker run --rm \
  --mount source=demo-data,target=/data \
  volume-demo


Output:
File from image


Docker copied the file into the empty volume.

4. Run with volume-nocopy
docker volume create demo-data2

That's because the mount hides the image's /data directory, and Docker was told not to copy its contents into the volume.

This Docker concept is called volume-subpath. It lets you mount only a specific subdirectory of a volume into a container, instead of exposing the entire volume.
docker volume create logs
 docker run --rm \
  --mount src=logs,dst=/logs \
  alpine mkdir -p /logs/app1 /logs/app2
 docker run -d \
  --name=app1 \
  --mount src=logs,dst=/var/log/app1,volume-subpath=app1 \
  app1:latest
 docker run -d \
  --name=app2 \
  --mount src=logs,dst=/var/log/app2,volume-subpath=app2 \
  app2:latest

 BIND MOUNT:

 When you use a bind mount, a file or directory on the host machine is mounted from the host into a container. By contrast, when you use a volume, a new directory is created within Docker's storage directory on the host machine. Docker creates and maintains this storage location, but containers access it directly using standard filesystem operations.


 Bind mounts are appropriate for the following types of use case:

Sharing source code or build artifacts between a development environment on the Docker host and a container.

When you want to create or generate files in a container and persist the files onto the host's filesystem.

Sharing configuration files from the host machine to containers. This is how Docker provides DNS resolution to containers by default, by mounting /etc/resolv.conf from the host machine into each container.

Bind-mounting over existing data:

If you bind mount file or directory into a directory in the container in which files or directories exist, the pre-existing files are obscured by the mount.(so the data in container will be hidden the data in the volume will be shown)


If you bind mount empty file or directory into a directory in the container in which files or directories exist, the pre-existing files are obscured by the mount.(so the data in container will become empty original will be hidden)

You can use the readonly or ro option to prevent the container from writing to the mount.
Bind mounts are created to the Docker daemon host, not the client.

docker run --mount type=bind,src=<host-path>,dst=<container-path>
docker run --volume <host-path>:<container-path>

source, src	The location of the file or directory on the host. This can be an absolute or relative path.
destination, dst, target	The path where the file or directory is mounted in the container. Must be an absolute path.
readonly, ro	If present, causes the bind mount to be mounted into the container as read-only.
bind-propagation	If present, changes the bind propagation.
bind-create-src	Automatically creates the source directory on the host if it doesn't exist. By default, --mount produces an error if the source path doesn't exist on the daemon.



docker run --mount type=bind,src=.,dst=/project,ro,bind-propagation=rshared


Recursive mounts
Imagine your Ubuntu EC2 host has this directory structure:
Host: /mnt/data/
├── file1.txt
└── backup/       ← A separate filesystem is mounted here
    └── backup.txt


You bind-mount /mnt/data into a container:
docker run -it --name test \
  --mount type=bind,source=/mnt/data,target=/data \
  ubuntu:latest bash


By default, Docker includes the nested mount at /mnt/data/backup as well.

Inside the container, you can see:
/data/
├── file1.txt
└── backup/
    └── backup.txt


The important point is that backup is not merely an ordinary directory; it is itself a mount point.
What does bind-recursive change?
Option	Behavior
enabled	Includes nested mounts; default behavior
disabled	Excludes nested mounts
writable	Includes nested mounts as writable
readonly	Includes nested mounts as read-only; requires Linux kernel 5.12 or later
